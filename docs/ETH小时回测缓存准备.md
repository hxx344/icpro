## 缓存如何加速

沿用现有数据层的两级缓存，不改变策略逻辑或缓存格式。月度层预先完成字段选择、UTC 时间转换、价格标准化和小时排序，以 Zstandard 压缩的 Parquet 保存。区间层合并所需月份，并保存小时切片索引，避免每次回测重新整理数千万行记录。

保留现有加载器需要的 19 个字段及 open/close 两种快照，不降低价格精度。源文件中的盘口数量和原始采样时间戳仍可用于策略审计。缺失报价回退遵循原加载器规则。

再次运行同一区间时，正式加载器自动命中区间缓存。同一进程内重复加载还会直接复用内存对象；修改回测区间时可复用各月份，首次生成新的区间缓存。缓存标识包含源文件路径、大小和修改时间，更新数据后自动生成对应的新缓存。

## 计时与验证

| 项目 | 本机耗时 |
|---|---:|
| 从月度缓存首次构建完整区间及索引 | 30.17 秒 |
| 清空进程内缓存后直接读取区间缓存 | 2.65 秒 |
| 独立 Python 进程通过正式加载器读取 | 2.60 秒 |
| 同一进程复用已有内存对象 | 约 3.05 毫秒 |

计时为本机单次测量，磁盘读取可能受操作系统文件缓存影响；正式加载耗时不含 Python 启动和导入，也不等于策略回测总耗时。30.17 秒包含首次写出区间数据，不能将其与 2.60 秒之比当作完整回测提速比例。最终准备及全量校验运行耗时 100.77 秒，复用了此前已生成的月度文件。

验证结果：

- 每个月重新从原始 Parquet 执行正式标准化规则，与月度缓存全部行和字段精确比较。
- 重新读取完整区间缓存，与月度缓存逐行核对；指数价格的跨月缺失值填充按加载器原规则单独核对。
- 旧缓存可能使用纳秒、新缓存可能使用微秒时间戳；比较时统一到 UTC 纳秒，要求实际时间值完全相同，其他字段仍精确比较。
- 52,844 个小时索引分组、两类可用时间列表均与重新计算结果完全相同；完成 444 次跨月份、快照类型的报价抽样核对。
- 独立进程验证禁止调用月度重建和索引重建路径，正式 `DataLoader` 仍成功加载全部记录，确认命中已生成的磁盘缓存。
- 20 项相关测试通过，覆盖缓存复用、源文件更新后增量重建、区间端点、旧时间精度、跨月指数价填充及既有报价查询语义；Ruff 错误检查通过。

## 使用

从仓库根目录重新准备或核验；已有有效缓存会复用，但此命令仍会读取原始数据进行全量核验：

```powershell
.\.venv-1\Scripts\python.exe scripts/data/prepare_hourly_backtest_cache.py --underlying ETH
```

普通回测继续使用现有加载器，无需先重复运行准备命令：

```python
from options_backtest.data.loader import DataLoader

store = DataLoader("data").load_hourly_option_store(
    "ETH", "2023-03-20 00:00:00", "2026-03-24 23:00:00"
)
chain = store.get_snapshot("2025-01-03 21:00:00", pick="open")
```

回测配置选择 `underlying: ETH` 和 `option_data_source: options_hourly`；完整区间终点使用 `2026-03-24 23:00:00`，只写日期会按原加载器语义截止当天 00:00。准备脚本另支持 `--start`、`--end`、`--data-dir` 和 `--report-dir`。
